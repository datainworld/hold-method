# 9장. 웹 프런트엔드 바인딩 (Modern Web Guidance)

> 초안 — v0.2 회고에서 유지 판정을 받은 규칙만 남긴다. 근거 등급: 가설 (실증 0회). 외부 근거(제작사 평가)는 HOLD의 등급을 대신하지 않는다.

HOLD v0.1의 통제 장치는 Python 백엔드용입니다. 웹 UI가 생기면 프런트엔드 코드는 안내도 통제도 없이 에이전트의 습관에 맡겨지고, 그 코드는 동작하므로 테스트를 통과합니다. 이 장은 이 빈틈을 Google Chrome 팀의 **Modern Web Guidance**(MWG)로 메우는 방법을 정합니다.

## 9.1 취지

- **무엇이 최신 웹 방식인지**는 MWG가 알려 준다. HOLD가 직접 가이드를 만들지 않는다.
- **어느 브라우저까지 지원할지, 어느 판의 가이드를 따를지**는 사람이 정한다(H1). 지원 기준은 기술이 아니라 이해관계자의 사용 환경에서 나오기 때문이다.
- 가이드를 따랐는지는 spec의 참조 가이드와 커밋 시점 검사로 남긴다(H4, H9).

## 9.2 왜 그대로 들이지 않나

MWG를 그대로 쓰면 HOLD 원칙과 부딪힙니다.

| MWG의 기본 | 충돌 | HOLD의 처리 |
| --- | --- | --- |
| `@latest`로 매번 받아옴 | 같은 코드가 어느 날은 통과하고 어느 날은 실패. 재현 불가 | 사람이 고정한 버전과 무결성 값(`hold.toml`), 검증된 사본으로만 실행 (R17) |
| 지원 기준·실험 기능 허용을 설정 명령·`.mwgrc`·CLAUDE.md로 바꿀 수 있음 | 에이전트가 정책을 바꿈(H1 위반) | 정책 원본은 `hold.toml`(보호 경로). 설정 명령은 래퍼가 거부 (R14, R17) |
| 업데이트를 사용자에게 권하라는 지시 | 에이전트가 사람을 설득해 버전을 올림 | 고정 skill에서 제거 |
| `legacy-scan`은 가이드의 약 20%만 | "통과"를 "최신"으로 오해 | 한계를 문서에 명시. 나머지는 안내로 남김 (H7) |
| 텔레메트리 기본 켜짐 | 공공 과제의 외부 전송 | 래퍼가 강제로 끔 |

## 9.3 통합 방법

**사람이 하는 일** (한 번, 그리고 MWG 버전을 올릴 때)

1. 이해관계자 정의서의 사람마다 **사용 환경**(기기·브라우저·망)을 적는다.
2. `hold.toml [web]`에 지원 기준(`baseline`), 대체 정책(`fallback_policy`), MWG 버전을 정한다. 버전은 `sync.py --pin`이 npm 무결성 값과 함께 고정한다.
3. 정한 정책이 `.mwgrc`·고정 skill·가이드 목록으로 생성되고 `lock.json`에 해시가 남는다. MWG 버전을 올리는 일은 방법론 개정이 아니라 프로젝트의 변경(`changes/`의 intent)이다.

**에이전트가 하는 일**

1. 프런트엔드 작업 전에 래퍼로 가이드를 찾는다: `python .claude/hold-web/mwg.py search|retrieve|list`.
2. spec의 `## 참조 가이드`에 읽은 가이드를 `mwg:<id>`로 적는다. 쓰지 않았으면 구체적인 이유를 적는다(R16).
3. 가이드가 대체 전략을 둘 이상 제시하면 고르지 않고 계약 질문으로 남긴다(R18).
4. 프런트엔드 파일을 바꾼 뒤 `web_scan.py`로 레거시 패턴을 검사한다. 오탐이라고 판단되면 코드를 비틀지 않고 보고한다(R15).

**기계가 하는 일** (커밋·CI)

- pre-commit: 설치·고정·생성물 대조, 사용 환경 값 검사, 참조 가이드 검사(R16), 레거시 검사(R15).
- CI: 확장 코드를 원본과 대조하고 원본 코드로 전체 검사를 다시 돌린다(`install.py --verify`).

## 9.4 단계별 적용

| 단계 | 적용 |
| --- | --- |
| 0 착수 | 이해관계자 정의서에 사용 환경 추가 |
| 1 Intent | 지원 기준 밖 사용자가 있으면 대체 정책을 intent에 적음 |
| 2 Design | 브라우저 지원 기준을 아키텍처 문서에 기록 |
| 2.5 계약 게이트 | 대체 전략 선택은 계약 질문 |
| 3 Build | 참조 가이드 표기(R16), 레거시 검사(R15) |
| 4 Verify | 검사 출력을 완료 증거로 첨부(H9) |
| 6 Maintain | 브라우저 관련 사고는 브라우저·버전을 적고, 원인이 지원 기준이면 사용 환경 갱신과 새 intent |

## 9.5 통제 대응표 (웹)

| R | 규칙 | 원칙 | 통제 장치 | 강도 |
| --- | --- | --- | --- | --- |
| R14 | 지원 기준·대체 정책·실험 기능 허용은 사람이 `hold.toml`에 정한다 | H1·H3 | 생성·보호·대조, 사용 환경 검사 | 부분 |
| R15 | 프런트엔드 코드는 고정 사본의 레거시 규칙을 통과하거나 사람이 허용 목록에 올린다 | H7 | pre-commit·CI 검사 | 부분 (규칙 ≈ 가이드의 20%) |
| R16 | spec은 참조한 가이드를 `mwg:<id>`로 적는다 | H4·H9 | 커밋 시점 검사 | 부분 |
| R17 | MWG는 사람이 고정한 버전·무결성의 검증된 사본으로만, 래퍼로만 쓴다 | H1·H10 | 래퍼, 무결성·재생성 대조 | 부분 |

(강도는 회고에서 다시 판정한다. 훅을 편입하면 R15·R17의 시점이 "수정 직후"로 앞당겨진다.)

## 9.6 프로필별 요구

Lite는 검사를 기록만 하고(`log`), Standard와 Regulated는 실패 시 커밋을 막습니다(`block`). 사용 환경 정의서는 Standard부터 필수이고, Regulated는 정책 변경마다 ADR을 남깁니다.

## 9.7 측정

`docs/hold/web-measurement.csv`에 변경마다 참조 가이드 사용 여부, 검사 결과, 허용 목록 사용을 적고 `web_check.py --metrics`로 집계합니다. 코어 측정 시트와 섞지 않아 실증 결과의 판이 구분됩니다.

## 9.8 알려진 한계

- 레거시 검사는 가이드의 약 20%만 다룬다. 나머지는 안내에 머문다.
- 정책 원본은 보호되지만 CLAUDE.md에 정책 같은 문구를 쓰는 것은 막지 못한다(R14).
- 변경 폴더와 코드 변경이 연결되어 있지 않아, 프런트엔드가 바뀐 변경에서 참조 가이드 생략을 거부하지 못한다(R16).
- 접근성 인증(KWCAG)과 프레임워크별 규칙은 다루지 않는다.
