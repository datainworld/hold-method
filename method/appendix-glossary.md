# 부록 A. 용어집

| 용어 | 뜻 |
| --- | --- |
| 가장자리 | 시스템이 외부 서비스와 맞닿는 지점. 네트워크 호출, 재시도, 호출 상한을 이곳에만 둔다 |
| 가짜 모델 | 실제 LLM 대신 미리 정한 응답을 순서대로 돌려주는 테스트용 모델 |
| 계약 | 모듈이 무엇을 받고 무엇을 돌려주는지에 대한 약속. 형태, 허용 범위, 의미, 실패 방식, 불변조건 |
| 계약 게이트 | Stage 2.5. 경계를 넘는 데이터를 사람이 확정하는 단계. 사람만 커밋할 수 있다 |
| 골든 테스트 | 고정된 입력에 대해 사람이 손으로 검산한 정답과 결과를 비교하는 테스트 |
| 관점 (viewpoint) | 특정 이해관계자의 관심사에 답하기 위한 다이어그램 작성 규칙. 그 규칙으로 그린 그림이 뷰 |
| 근거 등급 | 원칙이 얼마나 검증되었는지: 가설, 1회 실증, 반복 실증 |
| 마찰 기록 | 실증 중 방법론 때문에 생긴 불편·우회·낭비의 기록. 다음 판의 입력 |
| 모듈러 모놀리스 | 하나로 배포하지만 내부는 엄격한 경계를 가진 모듈로 나눈 구조 |
| 바이브코딩 | 사람이 자연어로 원하는 결과를 설명하고 AI가 코드를 작성하는 개발 방식 |
| 변경 폴더 | `changes/<YYYYMMDD-이름>/`. 한 변경의 intent·spec·plan·계약 초안을 함께 둔다 |
| 보호 경로 | 사람만 수정할 수 있는 경로 목록. `hold.toml`의 `[protect].paths` |
| 사실 뷰 | 이미 있는 구조를 코드·스키마에서 생성한 다이어그램. 손으로 고치지 않는다 |
| 산출물 체인 | 각 단계가 커밋해 다음 단계가 읽는 산출물의 연쇄. 감사 추적이 된다 |
| 서비스 에이전트 | 우리가 만들어 사용자에게 제공하는 AI 프로그램 (예: LangGraph 코디네이터) |
| 서비스 평가 | 서비스 에이전트의 행동을 실제 LLM으로 평가하는 테스트 |
| 안내 / 통제 | 규칙을 알려 주는 것(CLAUDE.md, 스킬) / 어기면 기계가 막는 것(훅, 검사) |
| 의도 뷰 | 앞으로 만들 구조나 흐름을 사람이 그리고 승인한 다이어그램 |
| 이해관계자 | 시스템에 요구·제약을 주거나 시스템의 변화에 영향을 받는 사람, 조직, 연관 시스템 |
| 이해관계자 정의서 | 이해관계자를 ID와 양방향 영향으로 정리한 표. `docs/architecture/stakeholders.md` |
| 집행 계층 | 다른 규칙이 정한 것을 기계가 지키게 하는 층 (4장 A3) |
| 코딩 에이전트 | 우리 대신 코드를 작성하는 AI (예: Claude Code) |
| 프로필 | 프로젝트 성격에 따라 필수 산출물을 조정한 묶음: Lite, Standard, Regulated |
| 하네스 평가 | 코딩 에이전트가 이 저장소의 규칙을 지키며 구현하는지를 평가하는 테스트 |
| 훅 | 특정 시점에 자동으로 실행되도록 걸어 두는 명령. PreToolUse(도구 실행 전), PostToolUse(실행 후) |
| ADR | Architecture Decision Record. 설계 결정 하나를 배경, 선택지, 결정, 결과로 짧게 남기는 문서 |
| C4 모델 | 소프트웨어 구조를 컨텍스트 → 컨테이너 → 컴포넌트 → 코드의 네 단계로 그리는 방법 |
| cid | correlation ID. 요청 하나에 붙여 모든 로그를 묶는 추적 번호 |
| Lite / Standard / Regulated | 6장의 테일러링 프로필 |
| Mermaid | 텍스트로 다이어그램을 쓰는 표기법. 마크다운 안에서 렌더링된다 |
| Outbox 패턴 | 보낼 이벤트를 DB 테이블에 먼저 기록하고 별도 작업자가 처리하는 방식 |
| UML | Unified Modeling Language. 시퀀스, 클래스, 상태, 활동, 배포 다이어그램 등을 정한 표준 표기 |
