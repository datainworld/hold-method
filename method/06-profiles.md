# 6장. 테일러링 프로필

방법론의 비용이 이득보다 크지 않도록 프로필 세 개를 둡니다. v0.1에서는 **Lite만 완전히 정의**하고, Standard와 Regulated는 "Lite에 무엇이 더해지는가"만 적습니다.

| 프로필 | 대상 | v0.1 상태 |
| --- | --- | --- |
| Lite | 개인·실험·1인 제품 | 완전 정의, 첫 실증 대상 |
| Standard | 소규모 팀의 제품 | 추가 항목만 정의 |
| Regulated | B2G 납품, 감리 대응 | 추가 항목만 정의 |

프로필은 `hold.toml`에 선언합니다.

```toml
[hold]
profile = "lite"   # lite | standard | regulated
```

`check_views.py`가 이 값을 읽어 필수 항목을 정합니다.

## Standard에서 더해지는 것

- **자동 리뷰.** 저장소 루트의 `REVIEW.md`에 리뷰 패스를 정합니다: Bugs, Security, Compliance(spec·plan 준수), Architecture(4장 안티패턴). CI가 이미 막는 것은 리뷰에서 빼고, 사소한 지적의 수에 상한을 둡니다.
- **하네스 평가.** `CLAUDE.md`, 스킬, 훅을 바꿀 때마다 실제 과거 작업 20~50개를 에이전트에게 다시 시키고, 결과를 경계·타입·보호 경로 검사로 채점합니다. 에이전트를 조종하는 설정도 코드처럼 회귀 테스트하는 것입니다.
- **운영 감시.** 지표 하나(예: 배포 후 오류율)에 이동 평균 기준선과 관리 한계선을 두고, 한계선을 넘으면 에이전트가 읽기 전용으로 진단해 새 intent.md를 씁니다. 감지는 결정론적 스크립트가 하고, 모델은 한계선을 넘은 뒤에만 부릅니다.

## Regulated에서 더해지는 것

- **감리 제출 산출물.** 정의서, 컨텍스트 뷰, 계약 클래스 뷰, ADR, 테스트 결과를 제출용으로 내보냅니다. 계약에서 인터페이스 정의서 양식(항목명, 타입, 길이, 필수 여부, 코드값)을 자동 생성하는 것은 v0.2 과제입니다.
- **관리 설정.** 권한 규칙, 샌드박스, 허용된 MCP 서버·플러그인만 쓰도록 중앙에서 관리하고, 개별 엔지니어가 끌 수 없게 합니다.
- **배포 게이트.** 운영 환경 배포는 지정된 승인자의 승인이 있어야 진행되도록 훅으로 막습니다.

## 프로필을 고르는 질문

1. 결과물을 나 혼자 쓰는가, 다른 사람에게 납품하는가? → 혼자면 Lite
2. 두 명 이상이 같은 저장소에 커밋하는가? → 그렇다면 Standard 이상
3. 감리·인증·제출 의무가 있는가? → 있다면 Regulated

프로필은 프로젝트 중간에 올릴 수 있습니다. 내리는 것은 이미 쌓인 산출물을 버리는 일이 되므로 권하지 않습니다.
